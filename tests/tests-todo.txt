 TIER 0 — FOUNDATION: make the suite runnable in isolation
--------------------------------------------------------------------------------
Purpose: every test runs against its own SQLite file. Never touch dev.db.

[ ] 0.1  Test database strategy
     - e2e runs use a separate DB via env:  DATABASE_URL=file:./test.e2e.db
     - PrismaService picks the better-sqlite3 adapter automatically when the
       URL starts with "file:" (server/src/prisma/prisma.service.ts:10).
     - Add a script in server/package.json, e.g.:
         "test:e2e": "DATABASE_URL=file:./test.e2e.db jest --config ./test/jest-e2e.json"
       (remove test.e2e.db before each run so tests start clean).
     - Do NOT run migrations in tests; push schema instead:
         npx prisma db push --schema prisma/schema.prisma   (pre-test)

[ ] 0.2  Keep the two smoke tests green
     - server/src/app.controller.spec.ts  -> npm run test
     - server/test/app.e2e-spec.ts        -> npm run test:e2e
     Reference: these prove the runner + Nest DI work before you add coverage.

[ ] 0.3  Create a reusable e2e bootstrap helper (recommended)
     - server/test/app.bootstrap.ts: builds the TestingModule, then mirrors
       main.ts so behavior matches prod:

         app.use(cookieParser())

     - Current e2e spec only sets the prefix and is missing the pipes/cookie

 TIER 1 — API E2E: CORE FLOWS  (server/test/*.e2e-spec.ts, supertest)
--------------------------------------------------------------------------------
Purpose: prove the happy path of every user-facing flow through the real HTTP
         stack (guards + pipes + throttler + DB). Run: npm run test:e2e

[ ] 1.1  Registration -> verification -> onboarding
     - POST /api/auth/sign-up                -> 201 (new user row exists)
     - (capture PIN from mocked MailService)
     - POST /api/auth/verify-account?token=  -> sets emailVerified=ts
     - POST /api/auth/resend cooldown        -> throttled/resend blocked
     - PUT /api/account/user                 -> name/bio/link update
     /!\ sign-up is throttled 5/10min -> keep this block isolated or bump ttl.

[ ] 1.2  Login / logout / session round-trip
     - POST /api/auth/login (valid)          -> 200 + Set-Cookie: st
     - GET /api/account/user with cookie     -> 200 current user
     - logout -> cookie cleared; old cookie now rejected
     - password wrong                         -> 401

[ ] 1.3  Threads: create, feed, detail, delete
     - POST /api/threads/post     (auth)     -> thread with postId
     - GET  /api/threads/posts               -> paginated feed (page param)
     - GET  /api/threads/post/:username/:postId -> detail
     - POST reply with parentId/rootId      -> thread chain persists
     - DELETE /api/threads/post/:id          -> owner only (403 for others)

[ ] 1.4  Likes & counters
     - POST /api/thread/post/like/:id        -> likesCount +1 (atomic)
     - POST /api/thread/post/unlike/:id      -> likesCount -1
     - duplicate like                         -> 409/200 idempotent (match impl)

[ ] 1.5  Follows & counters
     - POST /api/account/profile/follow/:username  -> followersCount +1
     - unfollow                                -> -1
     - duplicate follow                        -> 409/400 (match impl)

[ ] 1.6  Save / unsave
     - POST /api/thread/post/save/:id         -> saved list grows
     - POST /api/thread/post/unsave/:id       -> removed

[ ] 1.7  Activity feed notifications
     - POST a thread reply to another user    -> activity row (type reply)
     - @mention a user                        -> activity row (type mention)
     - like/follow                            -> activity rows (like/follow)
     - GET /api/account/activity/all          -> includes new entries
     - unread + mark-as-read endpoints        -> flags toggle

[ ] 1.8  Search + history
     - GET /api/search/:userId/:keywords      -> matching users
     - clicking result -> history entry; delete/clear history endpoints

[ ] 1.9  Password reset
     - POST /api/auth/forgotten-password      -> token row + email
     - POST /api/auth/reset-password/:token   -> password changed; old fails
     - expired token                          -> 400 (expiry check unit-tested too)

 TIER 2 — SECURITY & AUTH GUARD RAILS  (server/test/*.e2e-spec.ts)
--------------------------------------------------------------------------------
Purpose: prove the security posture an interviewer will ask about.

[ ] 2.1  Unauthenticated requests
     - no cookie -> GET /api/threads/posts, /api/account/user, etc = 401
     - confirm the exact guard contract for each controller (some may return
       204 via GetUserGuard instead of 401) and assert accordingly

[ ] 2.2  Guard + cookie validation
     - forged/random cookie value             -> 401 (session not found)
     - expired session row                    -> 401
     - deleted session (logout)               -> invalid

[ ] 2.3  Rate limiting (throttler)
     - login: 11th attempt within window      -> 429
     - sign-up: 6th within window             -> 429
     - global default 100/min endpoint        -> confirm 429 once exceeded
     /!\ Use a dedicated spec that overrides TTL or isolates these so the
         rest of the suite doesn't hit 429s from shared counters.

[ ] 2.4  DTO validation (global pipe)
     - malformed bodies (bad email, short password, extra fields) -> 400
     - whitelist: unknown props are stripped, not stored

[ ] 2.5  Authorization rails
     - non-owner cannot delete another's thread  -> 403/404
     - viewer-role test account blocked from account mutation endpoints
